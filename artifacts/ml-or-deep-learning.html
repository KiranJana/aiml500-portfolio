Title

Machine Learning or Deep Learning? A decision guide from two real systems

  • Artifact 2
  • Report
  • Machine learning
  • Deep learning

Introduction

When a team starts its first AI project, someone usually suggests deep learning, because it is behind the tools everyone is talking about. But a lot of the problems a backend team actually gets, like predicting which customers will leave or which tickets will escalate, start as rows in a database. This guide helps answer one question before anyone picks a model: does this problem need deep learning? It is based on a report I wrote comparing two documented production systems, one built with traditional machine learning and one built with deep learning.

Description

The report takes two examples from my course's lesson on machine learning and deep learning and ties each one to a real system described by the team that built it.

  • Machine learning: customer churn at SyriaTel. A Syrian telecom company predicted which customers would leave using XGBoost, a tree-based model, and reached an AUC of 93.3%. Features the team designed by hand, such as the share of a customer's contacts who used the competing network, raised the AUC from 84% to 93.3%. In a live test on 7.5 million prepaid customers, about 47% of the predicted churners who got a retention offer stayed (Ahmad et al., 2019).
  • Deep learning: Google Neural Machine Translation. Google moved all Chinese-to-English translation in Google Translate from its phrase-based system to a deep LSTM network with 8 encoder and 8 decoder layers. The new system reduced translation errors by an average of 60% in human evaluations. Training one basic English-to-French model used 36 million sentence pairs and took about 6 days on 96 GPUs (Wu et al., 2016).

Objective

I wrote the original report for Assignment 2.3 in AIML-500. The assignment asked for one machine learning example and one deep learning example from the lesson, a real-world application of each, and an explanation of why each approach fits its problem and why the other one doesn't. For this portfolio, I rewrote it as a guide for engineers and team leads who are deciding how to approach their first AI or ML feature.

Process

  1. Pick the examples. I chose two examples from the lesson that sit at opposite ends of its key differences: churn prediction works on business records that already fit in tables, and translation works on raw text. I passed on spam detection because the lesson uses it as both a machine learning and a deep learning example.
  2. Find real systems. I looked for cases documented by the teams that built them: SyriaTel's paper in the Journal of Big Data, and Google's research paper and announcement.
  3. Read the primary sources. I kept a source notes file with every number in the report next to the quote and page it came from. The journal's site asked for a login, so I read the authors' arXiv copy, which has the same page numbers.
  4. Check every claim. Each figure and quotation was checked against its source, and three sentences in the draft were cut because the sources didn't say them. One said the feature ranking guided SyriaTel's retention offers. The paper reports the ranking but never says that.
  5. Keep conflicting numbers apart. Google's announcement reports error reductions of 55% to 85% on several language pairs, and the paper reports an average of 60%. They come from different evaluations, so the report gives both and doesn't combine them.
  6. Test the comparison. A neural network churn model at another telecom company reported 91.1% accuracy. With about 5% of customers churning, a model that predicts "stays" for everyone is about 95% accurate, so accuracy can't show which model is better.
  7. Turn it into a decision. I turned the comparison into the flowchart above, using the lesson's key differences as the questions.

What I'd tell another team

  • Look at the form of your data before you pick a model. If it is already a table of fields people understand, start with a tree-based model. In a 2022 benchmark, tree-based models still performed best on medium-sized tabular data, about 10,000 samples (Grinsztajn et al., 2022).
  • Ask who will act on the result. A retention team needs reasons it can check. SyriaTel's team could rank which features drove the model's predictions. A deep network wouldn't give that ranking as directly.
  • Don't judge a model on accuracy when the thing you're predicting is rare. At 5% churn, a model that never predicts churn is 95% accurate. Use a measure such as AUC.
  • Deep learning earns its place when the signal is in text, images or audio. If your churn signal were in support tickets or call recordings, deep learning would be worth it, at least to turn that data into features. AIMultiple lists churn prevention from customer feedback as a deep learning use case (Dilmegani, 2026).
  • Count the cost first. A team without tens of millions of examples and a lot of computing power would struggle to build something like Google's system from scratch.

Value Proposition

This artifact shows that I choose a machine learning approach based on the data and the people who will use the result, and that I back each claim with a source someone else can check. For a team starting its first AI feature, it is a quick way to decide whether deep learning is worth the cost before committing to it.

Unique Value

Most comparisons of machine learning and deep learning are general lists of pros and cons. This one is built on two production systems described by the teams that built them, and every number traces to a page in a primary source. It also shows when the answer would change: the same churn problem would call for deep learning if the main signal were in free-text complaints instead of billing records.

Relevance

Teams are under pressure to add AI, and the best-known AI tools are deep learning models. Choosing deep learning when a simpler model fits costs computing power and makes the results harder to explain. The questions in this guide fit the first ML feature many teams build: predicting something from data they already store.
